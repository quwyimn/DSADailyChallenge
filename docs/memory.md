## Known gotchas / things proven to bite (watch for these)

- **Timezone is the #1 risk.** Store UTC, convert to GMT+7 only at the edges. The classic bugs: streak computed against the wrong "day", reset boundary off by the GMT+7 offset, leaderboard week rollover wrong. Test 23:59→00:00 early.
- **iOS blocks plain HTTP** — the production API must be HTTPS or the app silently fails to connect. (This is partly why we deploy early.)
- **iOS app suspension** — the user can background the app mid-task and return; the session store must restore the in-progress attempt or the user loses work.
- **Production ≠ local** in: CORS config, env vars, auth over HTTPS, Prisma→cloud-DB connection, timezone. These don't show up until deployed.
- **Drag-and-drop gestures** (linked list) feel different on a real iPhone than in a simulator — test on a real device.
- **Prisma 7 bans `url` in `datasource` block.** Adding `url = env("DATABASE_URL")` to `schema.prisma` fails validation with P1012. The URL must live exclusively in `prisma.config.ts → defineConfig({ datasource: { url: … } })`.
- **`prisma migrate diff --from-empty --to-schema prisma/schema.prisma --script` generates migration SQL without a live DB.** Use this to prepare migration files locally; apply with `prisma migrate deploy` once the DB is available. Never use `prisma db push` — it bypasses migration history.

- Storing local time in the DB.

## Bug journal (append as bugs are found & fixed)

- `[2026-06-13]` **Submission 409 + "Objects are not valid as a React child" → prod/local drift, plus a generic error-shape bug** → Reported crash on Challenge submit/resubmit. Root cause #1: `mobile/.env` pointed at the deployed Render backend, which still has the pre-"Allow Challenge Re-attempts" `if (existing) throw new ConflictException('Already submitted today')` (that fix exists locally but is uncommitted/undeployed — see technical debt log). Root cause #2 (general, affects ALL HttpExceptions, not just this 409): `GlobalExceptionFilter` sets the response's `message` field to `exception.getResponse()`, which for any built-in NestJS `HttpException` (`ConflictException`, `BadRequestException`, `NotFoundException`, ...) is an object `{statusCode, message, error}` — not a string. `mobile/src/services/errorHandler.ts`'s `parseApiError` only handled `data.message` being `string | string[]`, so it returned that whole object as `ApiError.message`, which `BubbleSortView`/`LinkedListView` then rendered via `<Text>{submitError}</Text>` → React "Objects are not valid as a React child (found: object with keys {message, error, statusCode})". → Fix: `parseApiError` now calls a new `extractMessage()` helper that recursively unwraps `.message` until it hits a string or `string[]`. → Lesson: any NestJS `HttpException` thrown with just a string message produces a nested `{statusCode, message, error}` body via `GlobalExceptionFilter` — mobile error parsing must always unwrap one level, not just check for `string | string[]`.
- `[2026-06-10]` **Leaderboard week-rollover ~1s gap** → `getHcmWeekRange()` computed `weekEnd` as HCM Sunday `23:59:59.000` (`+7d - 1000ms`), and `LeaderboardService.getWeekly` queries `createdAt: { gte: weekStart, lte: weekEnd }`. A submission landing in HCM Sunday `23:59:59.001`–`23:59:59.999` was `> weekEnd` for the ending week AND `< weekStart` (HCM Monday `00:00:00.000`) for the new week — counted in neither week's leaderboard. → Fix: changed `-1000` to `-1` so `weekEnd` = HCM Sunday `23:59:59.999`, closing the gap to <1ms. Covered by new `backend/src/common/utils/hcm-date.spec.ts`. → Lesson: when an inclusive (`lte`) upper bound is paired with an inclusive (`gte`) lower bound on the *next* range, the upper bound must be `nextLowerBound - 1ms`, not `-1s`.
- `[2026-06-13]` **Infinite loading on `expo start --web`** → `expo-secure-store@~15.0.8` (SDK 54) ships a web module that is a stub `export default {}` — none of `getValueWithKeyAsync`/`setValueWithKeyAsync`/`deleteValueWithKeyAsync` exist on web. `api.ts` already called the correct documented API (`getItemAsync`/`setItemAsync`/`deleteItemAsync`), but on web those threw `TypeError: ExpoSecureStore.default.getValueWithKeyAsync is not a function` inside `App.tsx`'s bootstrap effect, which never set `bootstrapped = true` → infinite spinner. → Fix: `persistToken`/`clearToken`/`getStoredToken` in `mobile/src/services/api.ts` now branch on `Platform.OS === 'web'` and use `localStorage` instead of `SecureStore`. → Lesson: `expo-secure-store` has **no web support at all** (not just a different API) — any code path that touches it must be Platform-gated before being used on web.
